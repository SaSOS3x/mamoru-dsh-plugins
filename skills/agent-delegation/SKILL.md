# Раздача работы агентам

Навык написан для DeepSeek Harness (инструменты `subagent`, `subagent_fork`, `send_message`,
`workflow`, `ask_user_question`). Цифры и выводы выросли из порта сборки DeceasedCraft на NeoForge
1.21.1 и проекта Space Journey (октябрь 2026) в Claude Code; они подписаны там, где это важно.
Метод от проекта не зависит, цифры токенов — от среды. Где поведение DSH не проверялось, это
сказано прямо.

Модель для агента выбирается по двум вопросам: есть ли у задачи готовый путь и что будет, если
агент ошибётся. Важность задачи тут ни при чём. Если путь задан (скрипт, спецификация, список
вопросов), дешёвая модель справляется не хуже сильной. Если пути нет и ошибку трудно заметить,
нужна сильная. Проверка нужна при любой модели: в прогонах порта DeceasedCraft проверяющие нашли
ошибки в 20 % пунктов у исполнителей на Opus.

Модель не задана в вызове, значит агент берёт модель сессии. Поэтому модель указывается в каждом
вызове явно, если сессия идёт на сильной модели.

## 1. Что оставить себе

Главная сессия ведёт разговор с пользователем, принимает решения, собирает итог и делает всё
необратимое: установку в рабочую папку, бэкап, git. Агента не стоит запускать на задачу в 1-3
вызова инструментов: у каждого агента постоянная цена входа (системный промпт, инструкции
проекта), около 60 тыс. токенов даже на чтение одного файла в Claude Code. Агент с настоящей
работой стоит 0,15-0,6 млн (цифры Claude Code с Claude 5, октябрь 2026; в DSH не перемерялись,
перемерь на своих задачах). Отдавать агенту стоит то, что займёт много чтения: обход папок и jar,
пачку однотипных файлов, независимые части большой задачи, проверку чужой работы. Мелкие задачи
по одной спецификации (в порте DeceasedCraft: теги, рецепты и квесты одного этапа) объединяй в
одного агента: три агента вместо одного - это лишние 120 тыс. токенов входа и три отчёта на сверку.

## 2. Какую модель брать

В DSH две модели: `deepseek-flash` (дешёвая, быстрая) и `deepseek-v4-pro` (сильная), и четыре
уровня усилия: `off`, `low`, `high`, `max`. Точный список маршрутов, доступных аккаунту, отдаёт
инструмент `list_subagent_models`, если он есть в сессии; поля `model` и `reasoning_effort`
принимает `subagent` (в пресете standard). `subagent_fork` модель не принимает: он наследует
модель родителя.

Колонка «Основание»: «проверено» относится к порту DeceasedCraft (2026-10) на Claude 5, а не к DSH;
«выведено» значит, что правило перенесено по смыслу, а не измерено в DSH.

| Работа | Модель | Усилие | Основание |
|---|---|---|---|
| Извлечь данные готовым скриптом: профили, логи, подсчёты, ответы по списку вопросов | deepseek-flash | low / high | проверено на Claude: 17 из 17 профилей |
| Обойти файлы и jar по ясным критериям, составить опись (только чтение) | deepseek-flash | high | проверено частично |
| Сделать по точной спецификации, когда решения приняты: генератор, теги, KubeJS, квесты, отчёт | deepseek-flash | high | проверено на Claude: реальный этап порта (генератор, теги, 3 квеста, отчёт) |
| Простейшее: есть ли файл, сколько строк, совпадает ли хеш, формат JSON | deepseek-flash | low | выведено |
| Нет готового пути: mixin в чужой код, поиск причины бага, дизайн с компромиссами, спорные источники | deepseek-v4-pro | high / max | выведено из опыта порта, в DSH не измерено |
| Проверить по чек-листу: сборка, тест, сверка с решениями, сверка с генератором | deepseek-flash | high | проверено на Claude: со списком утверждений и усилием high нашёл ошибки исполнителя (раздел 5) |
| Проверить Java / mixin по чек-листу с доступом к jar (javap, исходники) | deepseek-flash | high | проверено на Claude: нашёл crash-риск, пропущенный автором |
| Опровергнуть без чек-листа: новый worldgen, необратимое для мира, спорный дизайн | deepseek-v4-pro | max | применялось на Claude: порт и 10 ревью Space Journey (раздел 5), с дешёвой моделью не сравнивалось |

Если дешёвый агент вернул «не уверен», провалил проверку дважды или оказалось, что готового пути
нет, повтори на `deepseek-v4-pro` только этот пункт, а не весь прогон.

## 2a. Экономия токенов

Замер на проекте limb-damage 2026-11-02 (отдельный процесс читал журналы DSH, 2 часа, 393 шага):

| Показатель | Значение |
|---|---|
| input вне кэша | 995 731 |
| output | 337 093 |
| cache read | 146 512 896 (98 % объёма) |
| cache read на шаг | ≈ 372 806 |

Цена почти линейна по «длина контекста × число шагов»: каждый шаг заново читает весь накопленный
контекст, а собственный output — доли процента. Поэтому дешевле не «писать короче», а не пускать в
контекст лишнее и не делать лишних шагов.

1. Большие выводы не в контекст: списки jar, CSV, длинные логи считай скриптом и печатай 10–20 строк
   (`Select-Object -Last`, `--limit`, `grep -c`). Один дамп на 18 КБ стоит больше, чем весь разбор.
2. Дроби работу по этапам в отдельные сессии: свежая сессия с дневником дешевле, чем 3 часа в одной;
   перед новой сессией сожми дневник (project-journal).
3. Грузи только нужные навыки: 6 загрузок ≈ 50–60 тыс. токенов входа, повторно они не нужны.
4. Подагенты — для чтения чужого кода и логов: их контекст остаётся у них, в главную сессию
   возвращается сводка. Два агента в limb-damage дали две заметки вместо разбора 50 jar в главной сессии.
5. Стенд: сначала один диагностический прогон (мир, тип сущности, ориентация, сумма урона), потом
   проверки. Один провальный прогон стоит 3–6 шагов; 15 лишних итераций — 4–5 % общего объёма.

## 3. Что положить в промпт

Агент не видит разговор. Что именно он видит, зависит от инструмента:

- `subagent` — чистый контекст, беседы нет; видит только промпт и инструкции своего рабочего
  каталога (в DSH их подаёт `dsh-agent-instructions`: `AGENTS.md` и `CLAUDE.md` от корня проекта
  до рабочего каталога).
- `subagent_fork` — видит завершённые ходы этой беседы, но не текущий незавершённый ход; модель
  наследует от родителя. Годится, когда агенту нужен контекст разговора, а не пересказ.

В DSH `AGENTS.md` читается без импортов: строку `@путь` он не разберёт. Если проект лежит не в
папке сессии и не выше неё, положи `AGENTS.md` в папку сессии и перечисли в нём пути к проектным
файлам словами, либо открой сессию в папке проекта. Насколько свежий `AGENTS.md` получает
подагент, созданный после правки посреди сессии, в DSH не проверено: до проверки считай, что
новое правило надёжнее положить в промпт.

- Цель и признак готовности: что должно получиться и как это проверить делом.
- Решения пользователя дословно, с датой. Пересказ искажает смысл, а агент не может переспросить.
- Пути к нужным SKILL.md и к разделам журнала проекта, которые надо прочитать первыми. Путь к
  навыку дешевле и точнее пересказа.
- Агенту, который читает исходники чужого мода или библиотеки, дай тег или коммит, из которого
  собран jar у пользователя, и требуй ссылки файл:строка по нему: main бывает далеко впереди
  релиза (Space Journey 2026-10-14: main Starfold ушёл от тега v0.1.1 на 962 файла, PlanetRenderer
  Cosmonautics нашёлся только в невыпущенном main; оба раза поймал проверяющий).
- Запреты: куда писать нельзя (например, «только во временную папку, в рабочую папку и в
  запущенную программу не ставить»), какие файлы принадлежат другим агентам. Рабочий каталог
  подагента - каталог сессии, и команда с относительным выводом пишет туда (unzip без -d,
  jar xf, javac при внутренней ошибке кладёт javac.<дата>.args): дай готовые команды с
  абсолютным путём агента (Space Journey: 2026-10-21 класс Sable лёг в папку игры, 2026-10-25
  туда же файл javac).
- Формат ответа: изменённые файлы, запущенные проверки с их выводом, что не сделано, открытые
  вопросы и «ошибки по ходу» (что сорвалось или потребовало обхода, настоящая причина, как
  обошёл, что бы это предотвратило). Без этого пункта агент молча обходит ловушки, и следующий
  агент наступает на них снова. Структурированный ответ со схемой есть только у `workflow`
  (`agent(prompt, {schema})`); у `subagent` схему не передать, поэтому формат задавай текстом:
  «цитаты в ёлочках, пути с прямыми слэшами, длинный лог - путём к файлу, а не текстом».
  Невалидный JSON в StructuredOutput был в 10 вызовах из 421 (2026-09-09..23, DeceasedCraft и
  Space Journey), все в ответах больше 9 тыс. байт; из 75 ответов меньше 5 тыс. не упал ни один.
- Ловушки окружения: общие для проекта держи в `AGENTS.md` или `CLAUDE.md` (их получает каждый
  подагент своего рабочего каталога); в промпт или бриф пиши первым разделом лишь то, чего там
  нет. Агенты пропускают то, что стоит в конце.

Общую часть (пути, правила, решения) держи одной константой и добавляй ко всем промптам, а задание
каждого агента пиши отдельно.

### 3a. Промпт и план, проверенные делом

- Промпт агенту должен быть самодостаточным: абсолютные пути, вход и выход, формат, лимиты. Не
  ссылайся в нём на файл навыка или на «как описано выше»: у агента этого текста нет.
- План без проверенного артефакта (скрипт, команда, один прогнанный файл) не готов. Сначала
  прогони сканер или команду на одном реальном jar/куске лога, вставь в план цифры и только потом
  отдавай промпты: проверка на одном файле ловит `Expand-Archive` на `.jar` и неверный шаблон
  миксинов раньше, чем агент потратит прогон.
- Отчёт агента ограничивай форматом (10 строк, топ-N, лимит символов) и требуй evidence-файл;
  полный отчёт и дампы в главную сессию не возвращай.
## 4. Как запускать

- Параллельным агентам давай каждому свою подпапку для временных файлов: в общей папке они
  затирают друг другу одноимённые скрипты (ids.py) и импортируют чужие.
- Независимые агенты запускай одним сообщением (несколько вызовов `subagent` или
  `subagent_fork` в одном ходу) и продолжай работу, пока они идут; результат придёт уведомлением.
  Не жди их циклом и не опрашивай.
- `subagent` принимает `description`, `prompt` и, когда включён выбор модели в пресете,
  `model` и `reasoning_effort` из таблицы раздела 2. `subagent_fork` принимает `description` и
  `prompt`, модель наследует.
- У ожидания долгого прогона (опыт, серия, фоновая команда) есть предел и действие по нему: снять
  состояние (стеки потоков, хвост лога), погасить дерево процессов (на Windows
  `taskkill /T /F /PID <pid>`), записать. Тишина дольше обычного - событие, а не работа: в Space
  Journey замер 20 минут ждал признака, который с модом Sodium не наступает, а зависание выхода
  поймал только сторож с пределом 180 с, снявший стеки (2026-10-15..16). Предел ставь в сам
  прогон: фоновая команда в DSH запускается через `pwsh { run_in_background: true }` и живёт без
  таймаута, пока её не снимут `job_kill`; таймаут действует только у команды на переднем плане.
  Прогон на часы запускай отдельным процессом (на Windows Start-Process), в конце вывода печатай
  маркер и жди его через `job_output`.
- После прогона, который запускал процессы, сверь их список: скрипт, искавший JVM по имени папки,
  их не гасил, и три dev-сервера работали на одном порту (2026-10-15).
- `workflow` (только если пользователь согласился на мультиагентную работу): JS-скрипт, в нём
  `agent(prompt, {model, reasoning_effort, schema, label, phase})`, `pipeline(задачи, исполнитель,
  проверяющий)`, `parallel`, `phase`, `log`. Каждый исполнитель получает свой набор файлов, чтобы
  агенты не правили один файл. Кэша прогонов у `workflow` в DSH нет: повтор идёт с начала, поэтому
  дроби прогон на шаги и сохраняй промежуточные результаты сам. Запускай прогон сразу после
  сообщения, к которому он относится: агенты видят только свои промпты, и всё, что не попало в
  промпт, потеряно.
- После прогона запиши в журнал, сколько было агентов, на каких моделях и сколько токенов ушло
  (в DSH — по `session_stats`/итогам сессий, цифры `totalTokens` в Claude Code). Без этих цифр
  выбор модели в следующий раз будет на глаз.

## 5. Как проверять

- Отчёту агента не верь на слово. Ключевые пункты проверь сам: запусти тест или сборку, посмотри
  diff, открой файл.
- Проверяющий получает результат исполнителя и задачу найти ошибку. Если пункт не проверен делом,
  он считается непрошедшим. Промпт «подтверди, что всё хорошо» даёт согласие, а не проверку.
- Одного отчёта исполнителя проверяющему мало. Дай ему 5-12 главных утверждений исполнителя (тех,
  на которых держится результат; остальные проверь выборочно сам), команды его проверок и задание
  повторить сборку или генерацию в чистую папку и сравнить. В порте DeceasedCraft (2026-10-13)
  проверяющие Sonnet medium, получившие только отчёт на 40-60 тыс. знаков, проверили делом 8
  утверждений из 13. Sonnet high со списком утверждений и командами проверили 19 из 21 и нашли две
  ошибки, которые исполнитель пропустил. Менялись сразу список и усилие, вклад каждого отдельно не
  измерен.
- Свою работу главная сессия отдаёт на проверку так же, как работу исполнителя. В проекте Space
  Journey (2026-10-15) проверка замера, сделанного главной сессией на новом стенде, нашла 9
  дефектов, 3 из них меняли выводы; ревью её кода сборки №1 из 15 находок подтвердило 10, из них 4
  важные.
- Большое изменение (новый механизм, сотни строк, необратимое для данных) проверяй состязательно.
  На каждую область кода искатель находок; на каждую находку опровергатель с доступом к коду и
  заданием доказать, что она неверна, устарела или спорит с решением пользователя (CONFIRMED
  только делом: файл:строка, javap, прогон; иначе REFUTED или UNCERTAIN с прогоном, который
  решит); в конце критик полноты: что не искал никто, в том числе пропуски главной сессии. В Space
  Journey (10 ревью, 2026-10-15..23) в первых трёх опровергатели отсеяли 5 из 15, 5 из 11 и 5 из
  14 находок, в поздних почти всё подтвердилось; критик полноты дважды нашёл главное (падение
  сервера в тике; «неподвижный» шаблон мира, который менялся) и раз пропуск главной сессии
  (прежние тесты после правок не прогнали). Цена ревью 7-18 агентов, 1,4-3,4 млн токенов, около
  часа (Claude 5, октябрь 2026).
- Если рабочие файлы в это время меняет другой прогон, проверяющие читают замороженный снимок
  (diff от базы и копии файлов): в ревью по рабочему дереву часть находок пришла уже исправленной.
  Снимок с незакрытой временной правкой (мутацией) негоден.
- Утверждение агента о чужом коде (игра, мод, библиотека) принимай, когда за ним байткод или
  исходник версии пользователя по всему пути вызова, а не сигнатура; о логе - строка лога. Это
  касается и проверяющих: так оказались неверны «записи публичные, правка доступа (AT) лишняя»
  (они protected), «`difference` работает для любой реализации» (код игры ветвится по классу и
  выгрузил игроку 9 чанков) и «иначе корабли не сохранятся» (мод Sable сохраняет их сам).
- Замечания проверяющих вноси до установки. Если не согласен с замечанием, запиши почему.

## 6. Разбор ошибок

Агент знает о своих ошибках больше всех, поэтому причину спрашивают у него, а не угадывают по итогу.

- Агент вернул ошибку, упал, вернул пустой результат или проверка нашла у него ошибку: продолжи
  этого же агента через `send_message` и попроси короткий разбор: что сорвалось, настоящая
  причина, как обошёл, что бы это предотвратило. Новую работу при этом не давай. Агента, который
  закончил без ошибок, тоже стоит спросить, если у него было много вызовов: обходы он не всегда
  упоминает сам.
- Если агент умер (лимит, ошибка API) и продолжить его нельзя, посмотри `list_agents` и итог
  сессии ребёнка в интерфейсе DSH (или его сессию в `%USERPROFILE%\.dsh\sessions`: журналы
  подагентов лежат отдельными сессиями рядом с родительской) и запиши причину сам.
- Раз в этап прогони аудит сбоев по журналам сессии (навык session-error-audit: скрипт отбирает
  вызовы с ошибкой, в том числе с кодом возврата 0) и сверь с записанным. Пример из порта
  DeceasedCraft: в аудите 2026-10-12 из 27 типов сбоев 12 не были записаны нигде.
- Каждый разбор записывай в журнал проекта или навыка: шаг, причина, тип (ловушка окружения,
  неясное или неверное задание, ограничение модели или инструмента, ошибка в коде), что изменить.
  Свои ошибки главной сессии записывай туда же.
- Ошибка одного типа встретилась второй раз: это уже не случайность. Исправь источник (бриф,
  `AGENTS.md`, факт в навыке, инструмент) или предложи пользователю новый навык через
  skill-forge. Так система учится, а не повторяет одно и то же.

## 7. Расхождение с решением пользователя

Агент может сделать не так, как решил пользователь: отступить от решения, расширить его или
вывести следствие, которого пользователь явно не решал (пример из порта DeceasedCraft: «зомби в
защитном костюме тоже защищены» - вывод, которого пользователь явно не решал). Такое расхождение
не исправляется молча ни в сторону решения, ни в сторону агента: агент мог найти решение лучше,
пользователь мог ошибиться или быть прав.

- Сразу разбери: решение дословно; что сделал или предлагает агент и почему (спроси его через
  `send_message`, если причина не видна); к чему ведёт каждый вариант для результата, рисков и
  объёма работы; какой вариант рекомендуешь и почему.
- Покажи разбор пользователю одним вопросом с вариантами (`ask_user_question`), рекомендуемый
  вариант первым.
- Часть, которой касается расхождение, не ставь до ответа. Остальное можно делать дальше.
- Ответ пользователя запиши в журнал проекта как решение, с датой. Если агент оказался прав, это
  тоже урок: запиши, что помогло ему увидеть лучше.
- Чтобы расхождения находились, в промпте исполнителя и проверяющего проси отдельный пункт
  отчёта: «где результат отличается от решений пользователя или выходит за них».

## Ловушки

| Симптом | Причина | Решение |
|---|---|---|
| Все агенты работают на сильной модели, лимит кончается за один прогон | модель не указана и наследуется от сессии | указывать `model` в каждом вызове `subagent` |
| Агент нарушает правила проекта или изобретает уже сделанное | навыки и журнал проекта ему не передали | пути к SKILL.md и разделам журнала в промпте |
| Агент поменял рабочие файлы без бэкапа или при запущенной программе | в промпте не было запрета | «только во временную папку», установку делает главная сессия |
| Проверяющий одобрил то, что потом сломалось | его просили подтвердить, а не опровергнуть | «найди ошибку; не проверено делом значит не прошло» |
| Два агента затёрли правки друг друга | общий файл | делить по файлам, при нужде worktree |
| Прогон оборвался на середине | лимит сессии | перезапустить по шагам; кэша прогонов в DSH нет |
| Одна и та же ловушка у разных агентов | обходы не попадают в отчёт и в журнал | пункт «ошибки по ходу» в формате ответа, разбор (раздел 6) |
| Агент тихо сделал не по решению или главная сессия тихо «поправила» агента | расхождение не показали пользователю | раздел 7: разбор и вопрос пользователю до установки |
| Отчёт агента не появился, хотя работа сделана | файл-отчёт писать не велено или агент его не создал | результат - текстом; файл отчёта пишет главная сессия |
| Повторяются одни и те же сбои окружения у разных агентов | урок записан в журнал или навык, а подагент их не видит, или урок дописан в `AGENTS.md` посреди сессии | урок в `AGENTS.md` или в инструмент проекта, повторный аудит журналов сессии |
| Агент ищет пути, classpath и т. п. заново | в промпте нет точных подпутей и команд | давать точные пути, готовые строки команд и где лежат ещё не установленные файлы |
| У нескольких агентов сразу кончился GitHub API | лимит без токена (60 запросов в час) общий на IP для всех параллельных агентов | обходы в бриф до запуска: файлы через `raw.githubusercontent.com` или `cdn.jsdelivr.net/gh/<owner>/<repo>@<тег>/<путь>`, списки файлов через `data.jsdelivr.com` (Space Journey 2026-10-14: лимит кончился у всех 7 агентов исследования, у одного примерно через 15 вызовов; DeceasedCraft: у двух) |
| Агент не знает правил проекта, хотя они записаны в `AGENTS.md` | сессия открыта не в папке проекта, или правило дописано после старта сессии, или `AGENTS.md` не читается из-за `@импорта` (DSH импорты не разбирает) | сессия в папке проекта или `AGENTS.md` папки сессии с путями словами; правило, дописанное посреди сессии, - в промпты |
| Агент падает на первом же запросе, без вызовов: "safeguards flagged this message", `[reasoning_extraction]` | вероятно, промпт просит пересказать по шагам, что агент скажет пользователю и что сделает (2026-10-15: 18 из 18 вызовов, Opus и Sonnet; какая часть формулировки виновата, не выяснено) | дать обычную задачу: пробная папка с файлами, ответ пользователю в файл, итог со схемой в `workflow` (так прошли все 32 запуска того же теста) |

## Границы

Не нужен для задачи на несколько вызовов, для разговора с пользователем и для решений, которые
принимает пользователь. `workflow` запускается, только когда пользователь согласился на
мультиагентную работу. В остальных случаях подойдут один-два агента или работа самому. Если
агенты недоступны (нет `subagent`/`subagent_fork`/`send_message`), сделай задачу сам по тем же
пунктам 3 и 5; раздел 4 тогда не применяется. Названия инструментов и цифры токенов относятся к
среде: в DSH проверены только сами имена инструментов, цифры - из Claude Code.
