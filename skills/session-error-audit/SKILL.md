# Аудит ошибок сессии

Агенты в одном проекте наступают на одни и те же грабли, потому что урок записан там, куда они не смотрят. Подагент гарантированно получает только файл инструкций проекта (`AGENTS.md`, в DSH читается и `CLAUDE.md`), и то лишь из корня проекта вниз до рабочего каталога. Журналы, HANDOFF и навыки он читает, только если их назвали в промпте. Аудит отвечает на три вопроса: что падало (счёт по причинам), записано ли это там, где увидит каждый агент, и что исправить у источника.

Порядок важен. Сначала считаем по журналам сессии скриптом (2 секунды, без токенов), потом сверяем с записями, потом чиним источник, и только в конце, если ничего другого не помогло, пишем правило или навык.

## Когда запускать

- Раз в этап проекта и после большой задачи или `workflow` с агентами.
- Когда пользователь просит: "проверь ошибки сессии", "аудит ошибок", "почему агенты повторяют ошибки".
- Когда один и тот же сбой замечен в отчётах агентов второй раз.

Не запускай посреди работы над задачей: аудит читает уже законченные вызовы, а свежий хвост сессии почти весь состоит из вызовов самого аудита.

## Где лежат журналы DSH

```
%USERPROFILE%\.dsh\sessions\--<нормализованный cwd>--\session-<id>\session.v4.jsonl.zstd
```

Каждая сессия - своя папка с одним файлом; сессии подагентов лежат рядом такими же папками (`delegationDepth` в заголовке больше 0). Файл - конкатенация независимых Zstandard-кадров: `zstd -d` и модуль `zstandard` читают его целиком, а однокадровые API - нет. Поэтому скриптам нужен либо модуль `zstandard`, либо `zstd.exe` в PATH:

```
python -m pip install zstandard
```

Без них есть второй путь: в интерфейсе DSH меню сессии -> Download session log (команда `/export`) отдаёт ZIP, внутри которого те же строки лежат несжатыми как `session.vN.jsonl`. Передай скрипту ZIP или распакованную папку ключом `--export`.

События, на которых держится аудит: `tool/call` (`data.callId`, `data.name`, `data.arguments`), `tool/result` (`data.message.isError`, текст в `data.message.content`), `job/settled` (фоновая команда: `status`, `detail` с кодом возврата) и `user/message` (реплики пользователя во время работы).

## Цикл

### 1. Собрать (scan_fail.py)

```
python scripts/scan_fail.py --project "<папка проекта>" --out <рабочая папка>
```

`--project` берёт папку проекта и сам находит журналы в `%USERPROFILE%\.dsh\sessions` по имени папки `--<путь>--` (путь, где каждый знак кроме букв и цифр заменён на `-`), а если имя не совпало - сверяет `cwd` в заголовке сессии. `--sessions <корень>` задаёт другой корень журналов, `--export <ZIP|папка>` читает экспорт, `--session <id>` берёт одну сессию. `--since` / `--until` (UTC; лучше полная метка `2026-10-12T00:00:00Z`; принимаются также дата `2026-10-12`, `...T23:11Z`, `...+00:00`) режут период; время разбирается как время, а не как текст, мусор вместо времени останавливает скрипт с кодом 2.

Скрипт сопоставляет каждый вызов с его результатом (по `callId`, каждый id один раз) и пишет строку, если вызов упал. Жёсткий сбой: результат помечен `isError`, фоновая команда завершилась не с `completed`, или в выводе маркер `[exit code: N]` с N не 0. Мягкий сбой: `isError` нет, но в выводе `Traceback`, `No such file`, `is not recognized as the name of a cmdlet`, `NativeCommandError`, отказ в доступе, `Exception in thread`, `ModuleNotFoundError` и подобное. Результат: `rows.json`, `scan_meta.json` и `user_messages.json` (реплики пользователя для шага 3).

Если найдено 0 вызовов, скрипт печатает WARNING: это не "сбоев нет", а неверный период, `--session` или `--export`. Неверный ввод (нет папки, плохое время, плохой файл `--rules`) даёт строку `ERROR:` и код 2, без Traceback.

### 2. Разобрать (classify.py и show.py)

```
python scripts/classify.py --dir <рабочая папка> [--rules свои_правила.json]
python scripts/show.py --dir <рабочая папка> --cat STRONG
```

Каждая строка получает один из четырёх видов. Настоящий сбой делится на жёсткий (STRONG: `isError` или ненулевой код) и мягкий (SOFT: кода нет или он 0, но в выводе ошибка). Ожидаемое (EXPECTED) - нормальный ответ проверки: `git diff` вернул 1, `robocopy` вернул 1, проба отсутствия файла. Шум (NOISE) - слово из шаблона в успешном выводе: прочитанный файл, поиск по журналу, вывод самих скриптов аудита.

`show.py` показывает в каждой строке часть вывода с ошибкой (строки вокруг последнего маркера ошибки, а не начало), поэтому команда, которая сначала напечатала файл, а потом упала, видна по ошибке; `--part head` вернёт начало вывода, `--cluster <подстрока>` отберёт кластер.

После таблицы обязательно посмотри глазами (`show.py --cat STRONG`, `--cat SOFT`, по две-три строки из каждого кластера, на который будешь опираться): шаблоны ловят слова, а не смысл. Для причин, свойственных проекту, добавь свои правила в JSON (`where`: `out`, `cmd` или `tool`, плюс `cmd_pattern`, `out_pattern`, `not_pattern`). Нераспознанное, которое повторяется, получает правило, чтобы в следующем аудите не разбирать его заново.

### 3. Сверить с записями

Сначала, до таблицы, проверь, что инструкции проекта вообще доходят. DSH вставляет их отдельным сообщением с заголовком `Instructions from: <путь>`; в журнале сессии это видно поиском этой строки. Файл берётся из `AGENTS.md` или `CLAUDE.md` от корня проекта (ближайшая папка с `.git`) вниз до рабочего каталога; строку-импорт `@путь` DSH не разбирает, поэтому проект вне папки сессии сам не подключится. В проекте Space Journey (2026-10-15, Claude Code) сессия была открыта в папке игры, и текст `CLAUDE.md` репозитория не попал в начальный контекст ни одного из журналов агентов (около ста): все записи "есть в CLAUDE.md" там не доходили. Проверка: `Select-String -Path <журнал> -Pattern 'Instructions from:'` по распакованному журналу или `Select-String` по `user_messages.json` - в DSH инструкции приходят как пользовательское сообщение.

Потом для каждого настоящего кластера крупнее двух-трёх случаев ответь на два вопроса. Записано ли это вообще (grep по `AGENTS.md`, HANDOFF "Facts", журналам навыков, `skills/*/SKILL.md`)? Доходит ли запись до каждого подагента? Доходят: `AGENTS.md` проекта (если файл внутри цепочки от корня проекта до рабочего каталога) и сам инструмент (скрипт в проекте, который агент вызывает). Не доходят: журналы, HANDOFF, навыки, не названные в промпте. Запись вне этого списка считай отсутствующей. Насколько свежий `AGENTS.md` получает подагент после правки посреди сессии, в DSH не проверено; поэтому то же правило клади в их промпты. Итог - таблица "ошибка | сколько раз | где записано | доходит до агентов | что чинить".

Второй источник ошибок скрипт не видит: то, что не дало упавшего вызова. Это неверные допущения о чужом коде, пробелы в проверке, находки проверяющих и то, что заметил пользователь. Их бери из дневника проекта (поля "Проблемы", "Урок"), из отчётов проверяющих и из реплик пользователя; реплики за период лежат в `user_messages.json` (скрипт уже собрал их из `user/message`). В Space Journey за 2026-10-14..15 скрипт отнёс к настоящим 59 сбоев из 2101 вызова (проверка глазами нашла ещё 4 спрятанных и одну ложную), и стоили они по лишнему вызову, а самые дорогие ошибки шли этим вторым путём (например, все dev-клиенты до исправления шли без Sodium).

Это шаг суждения, не подсчёта. Его делает главная сессия или один агент среднего уровня (`subagent`) со списком файлов для чтения; результат всё равно просмотри сам.

### 4. Исправить источник, потом записать правило

Порядок по пользе, сверху вниз; останавливайся на первом, что убирает ошибку.

1. Убрать причину: переменная окружения, установленный модуль (например `zstandard` для этого навыка), права, маленький инструмент вместо угадывания (в проекте DeceasedCraft: `python _port/tools/jp.py <класс>` убрал "class not found" в javap, `eol.py` показывает окончания строк по байтам). Меняющее настройки делает пользователь или с его явного согласия.
2. Короткий блок в `AGENTS.md` (до 15 строк): правило, число случаев, пример. Только то, что должно дойти до каждого агента. До перезапуска сессии её подагенты новый блок могут не получить: то же правило клади в их промпты.
3. Дополнить существующий навык, если ошибка связана с его областью.
4. Новый навык только по правилам skill-forge: задача повторяется, без подсказки решается плохо, есть проверенный способ. Навык про ловушки окружения не создаётся: правило должно доходить до каждого подагента, а навык доходит не всегда.

Ничего из этого не применяй без пользователя: это инструкции для всех следующих сессий. Положи предложения в `skills-lab/` или покажи списком и жди ответа.

### 5. Записать в журнал

Запись "анализ" в журнал проекта: период, сколько вызовов, сколько настоящих сбоев (жёстких / мягких), топ кластеров, что решено чинить. Положи `summary.json` и `scan_meta.json` аудита в `audit-baseline/<дата>/` рядом с журналом проекта (не в папку навыка: в навыке они обновляются вместе с навыком): журналы сессий со временем чистятся, а сравнивать со старым счётом нужно.

### 6. Повторить на следующем этапе и сравнить

```
python scripts/compare.py --old <папка журнала проекта>/audit-baseline/<дата прошлого аудита> --new <рабочая папка>
```

Печатает по кластерам было / стало, число сбоев на 1000 вызовов, новые и исчезнувшие кластеры. Кластер упал - правка сработала. Кластер остался - правило не доходит до агентов или чинит не то (вернись к шагу 3). Новый кластер - новый вид ошибки, разбери его так же. Сравнивай на 1000 вызовов, а не абсолютные числа: объём работы за этап разный.

## Ловушки самого аудита

- Мягкий сбой не виден по коду возврата. Без разбора текста (шаблоны `SOFT` в scan_fail.py) аудит найдёт только жёсткие.
- Журналы DSH сжаты, и однокадровый распаковщик читает только первый кадр (в Node.js `zstdDecompressSync` так и делает): получается 200 байт вместо мегабайта, и аудит видит одну сессию. Проверка: `session_read.py --project <папка>` печатает число журналов и их пути; `--export` читает ZIP без сжатия.
- Аудит ловит собственный вывод: агент, запускающий скрипты аудита, печатает цитаты ошибок (UnicodeEncodeError, Traceback) и создаёт ложные строки. Мягкие строки команд, где упомянуты `scan_fail.py`, `rows.json` и т. п., скрипт уже относит к шуму. Такие же цитаты дают `Get-Content` / `Select-String` журналов проекта; их скрипт нарочно не прячет, чтобы не скрыть настоящую ошибку фоновой задачи в её выводе. Смотри их глазами и добавляй правило на команду.
- Искать журналы только в корне папки проекта нельзя: журналы подагентов - отдельные сессии в той же папке проекта, а не подпапки основной.
- Ожидаемое не равно ошибке: `git diff` с различиями тоже даёт код 1. Не добавляй такие строки в счёт и не "чини" их.
- В PowerShell 5.1 `2>&1` у нативной команды даёт `NativeCommandError` даже при успехе, а `$LASTEXITCODE` от прошлой команды приклеивается к новой с пустым выводом. Оба случая в правилах помечены EXPECTED с оговоркой `cmd_pattern`; если правило перестало срабатывать, посмотри `show.py --cat EXPECTED`.
- Текст ошибок Windows PowerShell в русской локали приходит в вывод инструмента искажённым (кракозябры вместо «Не удается найти путь»), поэтому судить по тексту нельзя: смотри `FullyQualifiedErrorId`, код возврата и наличие/отсутствие нужного файла. Для машинного разбора лучше процессы с английской локалью (`-Culture en-US` не всегда помогает: сообщения берутся из ресурсов ОС).
- Шаблоны построены под Windows PowerShell и английские сообщения, плюс несколько русских. Для другой оболочки или языка вывода часть строк окажется в STRONG/SOFT зря: прочитай их и добавь правила.
- Формат журналов меняется с версиями DSH (`session.v3`, `v4`). Скрипт берёт старшую версию в папке и не понимает новую молча: после обновления DSH повтори сохранённую базу (см. «Проверка результата»). Если числа разошлись больше чем на несколько строк, сначала проверь, не сменился ли формат.
- Журналы сессий чистятся по настройке DSH; старый счёт после чистки не восстановить, поэтому `summary.json` хранится.

## Проверка результата

Таблица в конце `classify.py` сходится: настоящие + ожидаемые + шум = число строк в `rows.json`. В каждом кластере, на который опираешься, глазами проверены 2-3 строки. Для повтора аудита на том же периоде: `--since` и `--until` из старого `scan_meta.json`, причём `--until` бери из поля `last_ts` (полная метка, например `2026-10-15T11:48:20.551Z`). Поле `until` бывает позже самого аудита, и тогда в повтор попадает работа после него (база Space Journey 2026-10-15: 3184 вызова вместо 2101). Числа совпадают с точностью до нескольких строк.

## Границы

Навык считает сбои вызовов инструментов; ошибки без упавшего вызова собираются вручную (шаг 3). Он не оценивает качество самих навыков (описания, ссылки на файлы, смесь метода с состоянием проекта): для этого есть проверка по skill-forge, шаг "Сопровождай". Он не заменяет раздел "ошибки по ходу" в отчётах агентов: тот сообщает причину сразу, аудит видит только то, что упало. Если нужен один сбой, а не сводка, читай журнал сессии напрямую (`session_read.py --project`).
